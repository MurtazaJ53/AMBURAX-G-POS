# AMBURAX POS — Architecture Decisions

ADR-001 ERPNext is ERP source of truth.
ADR-002 Clients use Amburax APIs, not privileged ERPNext access.
ADR-003 Original 81 retail screens are preserved.
ADR-004 Expanded Commerce/B2B/enterprise screens extend the foundation to 125.
ADR-005 Canonical product/variant identity belongs to Amburax.
ADR-006 Canonical order model normalizes all channels.
ADR-007 External IDs are mapping data.
ADR-008 Channel schemas are dynamic.
ADR-009 Channel allocation is policy, not authoritative stock.
ADR-010 Durable events/outbox power side effects.
ADR-011 Critical mutations are idempotent.
ADR-012 High-risk AI actions require approval by default.
ADR-013 Shopify first; Amazon/Flipkart next.
ADR-014 Meesho conditional on verified official access.
ADR-015 IndiaMART is primarily B2B/CRM.
ADR-016 Mobile is operational.
ADR-017 Microservices are logical first; extract physically with evidence.
ADR-018 Reconciliation is a first-class feature.
ADR-019 UI generation follows domain/API contracts.
ADR-020 Phase 1 Identity service is implemented as server-owned Next.js Route Handlers (apps/web) backed by its own Postgres schema (Tenant/Store/User/StoreMembership/Session/LoginAttempt/AuditLog), not a separately deployed microservice. Consistent with ADR-017/MICROSERVICES.md: split into a standalone identity service only when core-retail or another workload actually needs to scale, deploy, or fail independently from it. The service boundary is already logical (isolated under src/server/identity, no other module writes to its tables) so extraction later is a move, not a rewrite.
ADR-021 Login (A1) never issues a session for an account with mfaEnabled=true; it returns mfa_required and stops there until A2 (Verification/OTP/MFA) is built to complete the challenge. Identity data on this path is entirely Amburax-owned — no ERPNext read/write occurs during login.
ADR-022 Sessions are opaque, hashed, DB-backed tokens (not JWTs) specifically so A14 (Sessions/Devices) can list and revoke individual sessions server-side later without a token-blocklist workaround.
ADR-023 A2 (Verification/OTP/MFA): the mfa_required response from A1 carries an opaque, hashed, single-use MfaChallenge token instead of the raw userId (as A1 originally returned pre-A2). A raw userId in a client-facing "who are you verifying" field is a free enumeration/tamper primitive; a per-login opaque token bound server-side to one user, with its own expiry, attempt counter and consumed-at replay guard, is not.
ADR-024 OTP delivery goes through an `OtpNotifier` interface (`src/server/identity/notifier.ts`), not a vendor SDK call inline in the challenge service. No SMS/WhatsApp/email provider is connected yet — Notifications is Phase-1-scoped per MICROSERVICES.md but was not in A2's own scope to build. The shipped adapter logs to the server console and, only when `DEV_OTP_ECHO=true` and `NODE_ENV!==production`, echoes the code back to the client for local testing. This is disclosed, not hidden, and the real OTP hashing/expiry/attempt-limit/replay logic behind it is fully real — only the delivery leg is a stand-in.
ADR-025 Login-attempt rate limiting (`login_attempts` table) gained a `context` column (`password` | `mfa_verify` | `mfa_resend` | `password_reset_request`) so OTP brute-forcing, resend/SMS-cost abuse, and reset-request spam are rate-limited in their own windows and can't borrow headroom from, or exhaust, the plain-password login limiter.
ADR-026 A3 (Forgot Password): `POST /api/v1/auth/password/reset-request` returns exactly one of two shapes — rate_limited (429, safe to disclose: it describes the requester's own request volume, not the target account) or accepted (200, identical body for every other outcome: unknown email, disabled account, cooldown-throttled repeat, or a freshly issued token). The backend still branches internally and audits which case occurred; only the client-visible response is flattened to one shape. Fixed a pre-existing timing side-channel while here: A1's `login()` only ran bcrypt when a user was found, making "no such user" measurably faster than "wrong password" despite the identical response body. `requestPasswordReset` burns the same bcrypt cost on every silent-no-op path (unknown email, disabled, cooldown) via a shared `TIMING_SAFETY_DUMMY_HASH`; `login()` was patched the same way.
ADR-027 A password reset token supersedes (consumes) every prior unconsumed token for that user at issuance, and consuming a token also supersedes any others left over — only one reset link is ever valid at a time, closing the "requested twice, an old intercepted link still works" replay window. This is the documented policy DEVELOPMENT_RULES.md's screen checklist asks for; it did not exist before A3.
ADR-028 `OtpNotifier` (A2) is generalized to `IdentityNotifier` (`src/server/identity/notifier.ts`) with `sendOtp` and `sendPasswordResetLink` on one interface, rather than a second parallel notifier for reset links. Same disclosed dev-only console stand-in backs both; a real provider still doesn't exist for either.
ADR-029 Reset tokens are carried in the reset-link URL (`/auth/reset-password?token=...`), unlike A2's MFA challenge token which is deliberately kept out of the URL (sessionStorage handoff). This is not an inconsistency: an MFA code round-trips through the same tab in the same request; a reset link is delivered out-of-band by email and has to be a clickable URL to be usable at all. Standard practice (GitHub, Google, etc.) for exactly this reason.
ADR-030 `session.ts`, `mfaChallenge.ts`, and now `passwordReset.ts` all need "generate an opaque token, store only its sha256 hash" — extracted into `src/server/identity/token.ts` (`generateOpaqueToken`/`hashOpaqueToken`) instead of a third hand-rolled copy.
ADR-031 A4 (Reset Password) fixed a real race condition found while wiring `consumePasswordReset()` to a route: it read the token row, then separately ran an array-form `$transaction` that unconditionally updated it — two concurrent requests with the same token could both pass the "not consumed" check before either transaction committed, so the single-use guarantee wasn't actually atomic. Fixed by switching to an interactive transaction whose first statement is `updateMany({ where: { id, consumedAt: null, expiresAt: { gt: now } } })`; only one concurrent caller's `updateMany` can match, the loser sees `count: 0` and the whole transaction aborts before touching the password or any session. Covered by `passwordReset.consume.test.ts`'s "loses the claim" test (mocked Prisma — see BRUTAL TRUTH in the A4 delivery report for what that does and doesn't prove without a live database).
ADR-032 Introduced `passwordPolicy.ts` (`validatePasswordStrength`) as the first password-strength check anywhere in the codebase — A1 only ever compares against an existing hash, it never judged one. Length-based (8–200 chars) plus "at least one letter and one number", not special-character complexity, per NIST 800-63B guidance. `consumePasswordReset()` also now rejects a new password identical to the current one (checked via `verifyPassword` against the existing hash) before it will touch the transaction.
ADR-033 A4 deliberately does not create a session on successful reset. `POST /api/v1/auth/password/reset` never calls `createSession`/sets a cookie; the success response tells the client to route to `/auth/login`. AUTHENTICATION.md's side effect for this screen is session *revocation*, not creation, and CSRF risk analysis for this endpoint depends on it not carrying ambient session authority — see SECURITY.md's CSRF note.
ADR-034 The reset-password page reads `?token=` from the URL client-side and immediately calls `router.replace('/auth/reset-password', ...)` to drop the query param from the visible address bar and browser history before the user can act further. The token still transits as a URL once (unavoidable for an email link, see ADR-029) but this bounds how long it's visible/copyable/screenshot-able in the client. It does not, and cannot, prevent the token appearing in server-side access logs upstream of the app (reverse proxy, CDN) — that remains a deployment-level responsibility (redact query strings in access-log configuration).
ADR-035 A5 (Business Registration) introduces `OnboardingSession`, a fourth opaque-token model alongside Session/MfaChallenge/PasswordResetToken (all sharing `token.ts`'s generate/hash pair) — deliberately not a reuse of `Session`. A `Session` is the auth architecture's stated contract for "belongs to a real authenticated user"; at A5 there is no user yet, only a tenant being set up. Collapsing the two would either let a pre-auth registrant pass session checks meant for real accounts, or force `Session.userId` to become nullable and quietly weaken that guarantee for every other consumer of it. `OnboardingSession` grants no application access — only continuation of one tenant's own setup — and is tenant-scoped (`tenantId`), not user-scoped, because no user exists to scope it to.
ADR-036 `TenantStatus` (operational: ACTIVE/SUSPENDED) and the new `OnboardingStep` enum (setup progress: BUSINESS_CREATED → OWNER_CREATED → STORE_CREATED → TEAM_INVITED → POS_CONFIGURED → COMPLETE) are separate fields on Tenant, not one overloaded status column. "Is this tenant suspended" and "has this tenant finished onboarding" are independent questions — a suspended tenant could have completed onboarding years ago; a mid-onboarding tenant is neither active nor suspended in the operational sense. A6-A10 each own exactly one forward transition of `onboardingStep`; A5 implements only the first.
ADR-037 `POST /api/v1/tenants` is idempotent on a client-generated `idempotencyKey` (UUID), stored as `Tenant.registrationKey` (nullable, unique). A double-click, a browser retry after a timeout, or a resubmit-after-refresh all resolve to the same tenant. Because only the key's hash-equivalent (the key itself, used as a lookup value, not hashed — it's not a secret, it's a client-chosen dedup token) is stored, a replay cannot recover the *original* onboarding token (only its hash is ever persisted, per ADR-030's pattern) — so a replay correctly issues a *fresh* onboarding session for the *same* tenant rather than trying to resurrect the first one. A true concurrent race (two requests, same key, neither has committed yet) is resolved by letting the database's unique constraint decide: the loser's `create` throws `P2002`, is caught, and the loser fetches and returns the winner's tenant instead of erroring — no second tenant is ever created. See SECURITY.md's new "idempotent creation" pattern, generalized from this.
ADR-038 A5 does not call ERPNext. No ERPNext adapter exists yet (Phase 2 per PHASES.md); `Tenant.erpnextProvisionStatus` defaults to `NOT_PROVISIONED` and A5 never sets it to anything else. This is the "model the async state explicitly instead of pretending it completed synchronously" requirement satisfied honestly: the field exists so a future adapter has somewhere to record PROVISIONING/PROVISIONED/FAILED, but nothing here fakes that work happening now. Per ERPNEXT_DOCTYPE_MAP.md, Store (A7) is where ERPNext Warehouse/Company configuration actually becomes relevant — not Tenant.
ADR-039 A5 does not attempt duplicate-business detection by name or contact email. The only real uniqueness boundary at this stage is a tenant's `slug` (server-generated, always unique) and the idempotency key (ADR-037); `contactEmail` has no uniqueness constraint, because legitimate distinct businesses — and the same person operating multiple businesses — can share a contact email, and fuzzy name-matching produces false positives without a clear product-defined threshold. The account-level uniqueness boundary that actually matters (one login identity per person) is `User.email`, enforced at A6 when the owner account is created, not here.
ADR-040 Unlike A1-A4, `/onboarding/business` does not redirect an already-authenticated visitor away. A signed-in user's `User.tenantId` is a permanent, immutable link to their existing tenant (no multi-tenant user support in this schema); registering an unrelated second business while signed in is harmless and occasionally legitimate (a second business), so there's nothing to protect by blocking it.
ADR-041 A6 (Owner Account) expresses "owner role" as `User.tenantRole` (enum OWNER/STAFF), not a new `TenantMembership` join table, even though the user-supplied identity diagram for this screen used the words "Tenant Membership." `User.tenantId` is already a hard 1:1 FK — one user belongs to exactly one tenant, no exceptions anywhere in this schema — so a many-to-many join table would encode a relationship that can only ever have one row per user, duplicating a fact the FK already states. `tenantRole` captures the same real requirement (queryable "is this user the owner of their tenant") without the redundant table. This is distinct from `StoreMembership.role`, which genuinely is many-to-many (one user, many stores) and correctly stays a join table.
ADR-042 A6's concurrent-owner race is fixed the same way as A4's token race (ADR-031), generalized: the thing being atomically claimed is `Tenant.onboardingStep` itself (`updateMany({ where: { id, onboardingStep: 'BUSINESS_CREATED' }, data: { onboardingStep: 'OWNER_CREATED' } })` as the transaction's first statement), not the OnboardingSession. The OnboardingSession is deliberately NOT consumed at A6 — it stays valid for A7-A10, which reuse the same token. A retry that arrives after the tenant already has an owner returns `already_completed` and does **not** issue a fresh login session for the existing owner, unlike A5's idempotent-replay pattern (ADR-037) for the same class of "lost the race" case. The difference: A5's replay hands back a session-less onboarding continuation token; re-arming that costs nothing extra. Re-arming a full authenticated Session on every replay of a 48-hour-lived onboarding token would turn that token into a standing login backdoor for its entire lifetime, which exceeds AUTHENTICATION.md's stated scope for it ("grants no application access"). The safe fallback for a genuine lost-response retry is simply signing in normally at A1 with the password just set.
ADR-043 A6 creates a real authenticated Session on success (`createSession` + cookie), unlike A4's reset flow (ADR-033). This is not an inconsistency: A4 is a recovery flow where session revocation is the safety-relevant action; A6 is account *creation*, where establishing a session immediately after is standard signup UX and is what the owner-setup identity-hierarchy diagram this screen was built from explicitly calls for (ending in "authenticated Session").
ADR-044 A6 does not add a phone field to the owner account, despite the brief listing "phone where required" as a consideration. `User` has no phone column anywhere in the schema, and `Tenant.contactPhone` was already collected at A5 — adding a second, redundant personal-phone field to `User` without an actual consumer (no SMS-verification flow exists) would be exactly the kind of ungrounded field addition DEVELOPMENT_RULES.md warns against. If a later screen needs a per-user phone (e.g., SMS OTP as an MFA channel), that's the point to add it, backed by that consumer.
ADR-045 A6 does not treat "email already taken" as an enumeration risk requiring A3's generic-response treatment, and says so directly in the API response (`email_taken`, 409). This is a deliberate divergence, reasoned per SECURITY.md's "reserve the single-generic-response treatment for guessable/enumerable identifiers" principle (established in the token-possession note from A4): a *signup* form confirming "someone already registered this email" is standard practice industry-wide (Google, GitHub, etc.), carries materially lower risk than confirming an *existing account's* details during login/reset (the attacker learns nothing they couldn't already infer by trying to log in or reset that email elsewhere), and blocking it silently would make legitimate double-signup attempts undebuggable for the user with no compensating security benefit.
ADR-046 A7 (Store Setup) confirmed `StoreMembership` (present since the original schema) is already the correct multi-store access model — a genuine many-to-many join (`@@unique([userId, storeId])`, free-text `role`) distinct from `User.tenantRole` (ADR-041). No new join model was introduced; A7 only had to use the existing one correctly: create one `StoreMembership(role: 'OWNER')` row per first store, scoped to the store, not inherited automatically from tenant ownership. This is the structural basis A12 (Store/Workspace Selection) will read from — a user's available stores are exactly their `StoreMembership` rows, already queryable, already correct for N stores per user and N users per store.
ADR-047 `Store` is the Amburax-side location/warehouse concept; no separate `Location`/`Warehouse` model was introduced. ERPNEXT_DOCTYPE_MAP.md already states "Store -> Warehouse/Company setup," and DOMAIN_MODEL.md's original Store definition already folds in "location, warehouse, timezone." A second table would either duplicate Store 1:1 for no reason, or become a second, non-ERPNext-authoritative inventory-location concept — exactly what DEVELOPMENT_RULES.md and ERPNEXT_COVERAGE.md forbid. `Store.erpnextProvisionStatus`/`erpnextWarehouseId` (reusing Tenant's existing `ErpnextProvisionStatus` enum, not a new one) are where a future ERPNext adapter records Warehouse provisioning against this same row.
ADR-048 A7 does not call ERPNext and does not build an adapter interface with no caller. No ERPNext adapter exists yet (Phase 2); rather than add a speculative `ErpnextAdapter` TypeScript interface that nothing implements and nothing invokes — itself a form of the "dangerous half-integration" this build was explicitly warned against — the boundary is documented here and in ERPNEXT_DOCTYPE_MAP.md as a contract for Phase 2 to implement, and `Store.erpnextProvisionStatus` stays at its `NOT_PROVISIONED` default. This mirrors A5's identical deferral for Tenant (ADR-038): a real field, honestly unset, beats either a fake success or an unused code stub.
ADR-049 A7's concurrent-first-store race is fixed with the same shape as A6's (ADR-042) and A4's (ADR-031): the transaction's first statement conditionally claims `Tenant.onboardingStep` from `OWNER_CREATED` to `STORE_CREATED`. No client-supplied idempotency key is used or needed here (unlike A5, ADR-037) — the Tenant and its owner already exist by A7, so the onboarding-step transition itself is already the correct, sufficient one-time gate; a second client-generated key would be redundant machinery solving a problem the step field already solves.
ADR-050 A7 authorizes on `session.user.tenantRole === 'OWNER'`, resolved entirely server-side from the session cookie — the request body carries no `tenantId`, `ownerId`, or `storeId` field at all, so there is nothing for a client to forge. This is deliberately stricter than "any authenticated user of this tenant": once A8 (Team Invitation) exists and a tenant has `STAFF` users, they must not be able to call this endpoint merely by having a valid session for the same tenant.
ADR-051 A8 (Team Invitation) introduces `Invitation`, a fifth opaque-token model, deliberately not sharing a table with Session/OnboardingSession/PasswordResetToken/MfaChallenge — see AUTHENTICATION.md's "pre-auth credential types." Status (PENDING/ACCEPTED/REVOKED/EXPIRED) is derived from three nullable timestamps, not stored as an enum, continuing the same convention as every other token model in this schema — one source of truth per fact.
ADR-052 `StoreMembership.role` stayed a free string (not upgraded to a schema enum) even though A8 needed to restrict which roles an invitation can grant. Changing a working column's type would be exactly the "rebuild working infrastructure" the brief said not to do. Instead, `src/server/tenant/storeRoles.ts`'s `INVITABLE_STORE_ROLES` allow-list enforces the restriction in code, at invitation creation, and is the same list A11 must reuse when it later creates the StoreMembership row from an accepted invitation. `OWNER` is permanently excluded — tenant ownership is established exactly once, at A6 (ADR-041), never through an invitation payload.
ADR-053 A8's wireframe shows both "Skip" and "Continue" buttons, which settles what would otherwise be an ambiguous product question: does `TEAM_INVITED` require at least one invitation, or just that the step was explicitly completed? It's the latter. `completeTeamStep()` (`POST /api/v1/onboarding/team/complete`) is a separate operation from `createInvitation()` — advancing onboarding never happens as a side effect of inviting someone, and creating zero invitations plus pressing Skip is a fully supported path, using the same atomic-claim shape as A6/A7 (ADR-042/ADR-049) on `STORE_CREATED -> TEAM_INVITED`.
ADR-054 A real concurrency bug was found and fixed during A8's own construction, before it shipped: the original `createInvitation()` superseded any existing pending invitation for (tenant, store, email) with a read-then-write inside a transaction (`updateMany` to revoke, then `create`). Two overlapping double-click requests could each observe "no pending invite yet" before either committed, producing two live invitations for the same email+store — the exact class of bug A4/A6/A7's atomic-claim fixes exist to prevent, just not yet applied here. Fixed by adding `@@unique([tenantId, storeId, email])` to `Invitation` and replacing the transaction with a single atomic `upsert` (`INSERT ... ON CONFLICT DO UPDATE`) — one row per (tenant, store, email) forever, refreshed (new token, new expiry, cleared accept/revoke state) on every new invite. This is a stronger fix than a conditional `updateMany` claim would have been: it's a single database statement, not two, so there's no window between them to race in at all.
ADR-055 Inviting an email that already belongs to a *different* tenant is rejected outright at creation (`email_unavailable`), not deferred to A11. `User.email` is globally unique (no multi-tenant user support anywhere in this schema — see ADR-040), so such an invitation could never be accepted regardless of how A11 processes it; failing fast avoids sending a real notification for an invitation that is dead on arrival. Inviting an existing member of the *same* tenant to a second store is allowed and goes through the identical invite+token+A11 flow as a brand-new user — no separate "instant grant" mechanism was built, since one consistent, audited path for both cases is simpler and instant grants belong to screen 67 (Users/Roles/Permissions), not onboarding.
ADR-056 A11 (Staff Invitation Acceptance) never verifies a password itself. For an invited email that already has an account, acceptance requires an **already-authenticated session for that exact email** — the invitation token alone can never bind an existing identity. The reason is concrete, not stylistic: A1's login routes `mfaEnabled` users through an MFA challenge before issuing a session, so a second password-verification path inside A11 would have been an MFA bypass for any existing account with MFA on, reachable by anyone holding the invite link. Reusing A1/A2 wholesale is the only way to guarantee the invitation path can't drift from the authentication path. The cost is a UX seam (sign in, then reopen the link) accepted deliberately over building a `next=`-style redirect, which would add an open-redirect surface to a public, token-bearing URL.
ADR-057 A11 issues a Session only on the **new-account** path, never the existing-account path. New account is account creation with a self-chosen password, which A6 already established as session-worthy (ADR-043), and possession of an emailed link is the same class of identity proof A3/A4 rely on. An existing account already has its own session; minting a second one from token possession is precisely the account-takeover path this screen exists to prevent.
ADR-058 An authenticated visitor may only accept an invitation addressed to their own email (`identity_mismatch` otherwise). This blocks "invitation for alice@ opened by signed-in Bob → Bob gets Alice's membership", and also prevents a confusing silent session swap if a logged-in user opens an invitation for an unregistered third-party email.
ADR-059 A11's acceptance transaction claims the invitation **first**, before creating or loading the User: `updateMany({ where: { id, acceptedAt: null, revokedAt: null, expiresAt: { gt: now } } })` is statement one, then user create-or-load, then `acceptedByUserId` binding, then StoreMembership — all in one interactive transaction. Claim-first is deliberate: it locks the invitation row for the transaction's whole life, so a concurrent acceptance blocks and then fails cleanly having written nothing, rather than performing user-creation work that must be rolled back and contending on the `User.email` unique index. Because all four statements share one transaction, no User, membership, or `acceptedByUserId` can ever outlive a failed claim. Session creation is deliberately *outside* the transaction (A6 precedent): a transient session-write failure must not roll back an otherwise-valid acceptance — the user can simply sign in.
ADR-060 A11 re-validates the invitation's stored `role` against `INVITABLE_STORE_ROLES` at acceptance time, not just at creation (A8). The allow-list can change between issuance and acceptance, and a week-old invitation row must not be able to grant a role that is no longer invitable. `StoreMembership.role` is written from the invitation, never from the request body; `User.tenantRole` is always `STAFF` on this path.
ADR-061 A9 (POS Setup) introduces `PosDevice` as its own model rather than reusing Store, User or a "device-as-user" workaround. A POS terminal is an operational device: it does not log in, holds no role, has many-per-store cardinality that Store cannot express, and must be revocable without touching any person's identity. OFFLINE_POS.md section 9 already requires exactly this shape (Tenant -> Store -> POS Terminal -> Device) so the server can attribute every offline transaction to the device that produced it, and section 8's idempotency key (tenant + store + device + local_transaction_id) is unbuildable without a stable device id. Fields are grouped into identity / credentials / configuration / runtime, and runtime (`lastSeenAt`) is deliberately not stored as configuration - heartbeat, online/offline and sync state belong to the offline engine (OFFLINE_POS.md section 4), not to an onboarding form.
ADR-062 `PosDevice.createdAt` and `PosDevice.activatedAt` are separate facts, and A9 reports them separately. A row created by the setup screen means "the merchant configured a terminal"; it does NOT mean a physical device exists, has been paired, or can sell. Status is derived (PENDING_ACTIVATION / PAIRING_EXPIRED / ACTIVE / DISABLED) from nullable timestamps, matching the Invitation/PasswordResetToken convention, and the A9 success screen says "awaiting pairing", never "POS ready". Treating row-exists as terminal-ready would be exactly the fake completion this architecture forbids.
ADR-063 A9 deliberately does NOT collect invoice prefix, invoice start number, default customer or price list, even though the A9 wireframe sketches them. Invoice numbering is ERPNext-authoritative (OFFLINE_POS.md section 10: "Server-side/ERPNext invoice numbering remains authoritative") and an Amburax-side start number would be a second authoritative counter - the duplicate-authority failure ADR-001/ERPNEXT_COVERAGE.md exist to prevent. Default customer and price list are ERPNext-owned records that no Amburax model or adapter can validate against yet; a free-text field there would persist an unvalidated string that later screens would treat as authoritative. A9 collects only what Amburax genuinely owns and can honour today: terminal identity, receipt header/footer, and counter behaviour (product images, scan sound, cash drawer). These fields return with screen 74 (POS Configuration) once the ERPNext adapter can resolve them.
ADR-064 A POS terminal is not an ERPNext document and `PosDevice` carries no `erpnextProvisionStatus` field. Unlike Tenant->Site (ADR-038) and Store->Warehouse (ADR-047), which have documented ERPNext mappings, ERPNEXT_DOCTYPE_MAP.md defines no terminal doctype: what ERPNext owns for a till is the Sales Invoices and Payment Entries it will later post, not the till itself. Adding a provisioning-status column with no pipeline behind it would imply an integration that does not exist - the same "uncalled adapter reads like integration" anti-pattern SECURITY.md already rejects.
ADR-065 Device registration is a two-credential pairing exchange, designed here because no MD file specified one. A9 issues a one-time pairing code (CSPRNG, ~100 bits, Crockford base32 with no look-alike characters, short TTL, sha256-hashed at rest, shown to the human exactly once); `POST /api/v1/pos/devices/activate` consumes it and issues a separate long-lived 256-bit device secret to the machine, also stored only as a hash. Two credentials rather than one, because a single code would make the string a merchant reads off a setup screen the terminal's permanent credential. Neither reuses Session, OnboardingSession, PasswordResetToken, MfaChallenge or Invitation - a device credential has a different subject (a machine), lifetime and revocation story; only `token.ts`'s hash helper is shared. The activation endpoint is unauthenticated by design: the caller is a terminal, and possession of the pairing code authorizes exactly one narrow action, conferring no user authentication and no store access - the same posture ADR-056 established for invitation tokens.
ADR-066 Revocation is `PosDevice.disabledAt`, never deletion. Sales will reference `posDeviceId` for the life of the business, so a compromised or retired terminal must be disableable without destroying its transaction history; `derivePosDeviceStatus` ranks DISABLED above every other state, and activation refuses a disabled device even when the pairing code is otherwise valid.
ADR-067 A9's onboarding transition accepts BOTH `STORE_CREATED` and `TEAM_INVITED` as predecessors of `POS_CONFIGURED`. ADR-053 made the team step genuinely skippable, which means a legitimate tenant can arrive at A9 sitting at either step; enforcing only `TEAM_INVITED` would have made onboarding uncompletable for every tenant that pressed Skip. A9 also mirrors ADR-053 itself with its own Skip button: `POS_CONFIGURED` means "the POS step was completed", not "a terminal exists" - a warehouse-only location has no till to configure.
ADR-068 POS configuration is authorized by a store-scoped capability, not by tenant ownership alone: `posRoles.ts`'s `canConfigurePos` admits a tenant OWNER (who owns every store by definition) or a `StoreMembership` on that exact store with a role in `POS_CONFIGURABLE_STORE_ROLES` (OWNER, STORE_MANAGER). Deliberately a second allow-list rather than a reuse of `INVITABLE_STORE_ROLES` (ADR-052), which answers a different question - merging them would mean widening who can be invited in order to widen who can configure a till. Skipping the step stays owner-only, because that is a tenant onboarding decision rather than a store operation. A CASHIER membership grants no POS-configuration capability.
ADR-069 Every authenticated server component now degrades to a readable "Temporarily unavailable" screen when the datastore is unreachable, instead of Next's raw HTTP 500. Found at A9 by smoke-testing with the database deliberately down: `/home`, `/onboarding/store`, `/onboarding/team` and `/onboarding/pos` all returned 500, while every API route and A11's public `/invite/[token]` page already degraded politely. Only the data-loading calls are wrapped - never `redirect()`, which Next implements by throwing and which a careless try/catch would swallow.
ADR-070 ADR-010's durable outbox is implemented as a single `outbox_events` table written by the *same* PostgreSQL transaction as the business mutation it describes, enforced by the type signature: `enqueueOutboxEvent` accepts a `Prisma.TransactionClient` and nothing else, so it is not possible to write an event on the global client. This is deliberately NOT a replacement for `AuditLog`. The two coexist and answer different questions: `writeAuditLog` uses the global client at all 53 of its call sites, so an audit row survives a rollback and is missing if the process dies after commit - acceptable for an operator's action trail, fatal for a domain event something downstream must act on. AuditLog answers "who did what"; OutboxEvent answers "what must happen next". Envelope fields are EVENTS.md's "Event requirements" list verbatim. Delivery state is derived from nullable timestamps (publishedAt / deadLetteredAt), matching the Invitation/PasswordResetToken/PosDevice convention rather than adding a status column that can drift.
ADR-071 Outbox delivery is **at-least-once**, not exactly-once, and consumers are required to be idempotent (EVENTS.md already mandated this). Exactly-once across a database and a separate transport needs distributed transactions; claiming otherwise would be a guarantee the system cannot keep. Producer-side duplication is prevented by a deterministic `idempotencyKey` (`tenant:eventType:entity:discriminator`) under a unique index, so a retried operation collides instead of enqueuing twice - but a rolled-back transaction leaves no row, so a genuine retry is free to insert, which is exactly right. A duplicate key is allowed to throw rather than being swallowed: because it runs inside the caller's transaction, swallowing it would hide a real double-emit bug while the business mutation committed anyway.
ADR-072 (amended 2026-09-12: the claim's ORDER BY selects *which* rows are taken, but PostgreSQL guarantees no ordering for rows returned by `UPDATE ... RETURNING`. The dispatcher therefore sorts claimed rows by `occurredAt` before publishing; without that, oldest-first delivery was accidental and failed roughly two runs in three.) The dispatcher claims work with `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED)` in one statement, advancing `attempts` and pushing `nextAttemptAt` forward *before* publishing. Two consequences, both deliberate: several dispatchers can run concurrently without ever being handed the same row, and a dispatcher that crashes mid-publish cannot hot-loop because the row is already scheduled into the future. Backoff is exponential from 30s capped at 1h; a row is dead-lettered after 8 attempts so a permanently undeliverable event stops consuming dispatcher budget instead of starving healthy ones. `lastError` is scrubbed through P0-2's `sanitizeText` before being persisted - it is read back by operators and would otherwise become a durable copy of a leaked credential.
ADR-073 No message transport exists, and the outbox does not pretend otherwise. Delivery goes through an `OutboxPublisher` interface whose only implementation logs and reports success, the same disclosed stand-in pattern as `IdentityNotifier` (ADR-024/028) where the real logic is complete and only the delivery leg is a placeholder. What is genuinely real here is the durability: transactional insert, row-locked claiming, retry, dead-lettering. "Published" currently means the local stand-in accepted the event, not that anything received or acted on it. Swapping this one interface for a real transport changes nothing else.
ADR-074 `PosDeviceCreated` from A9's `createFirstPosDevice` is the first and, for now, only wired producer. The remaining events in EVENTS.md stay audit-log-only and migrate to the outbox as each producer is revisited, rather than being converted speculatively in bulk. Event payloads carry ids and configuration only - never a pairing code, device secret, token or password hash, because an outbox row is replayable and readable by every future consumer long after the credential it mentions was rotated.
ADR-075 Onboarding resume is decided server-side at `/home`, and nowhere else. Every authenticated entry path - A1 sign-in, A2 MFA completion, the `/` root redirect, a bookmark, a browser refresh - already lands on `/home`, so one guard there covers all of them without a client ever deciding where onboarding stands. The decision reads `Tenant.onboardingStep` and Store existence scoped by the session's `tenantId`; nothing is accepted from a request body, query string or cookie. Two guards sit on top of the step mapping. Only a tenant OWNER is resumed: a STAFF user admitted by A11 may belong to a mid-onboarding tenant, but every onboarding page would reject them, so redirecting them would be a guaranteed bounce. And a tenant whose step implies a Store that does not exist is NOT resumed - `/onboarding/pos` sends a storeless tenant to `/onboarding/store`, which only accepts OWNER_CREATED, which returns to `/home`, so following the mapping there would be an infinite redirect loop. That state is corrupt data rather than an unfinished step (A10's readiness already calls it `inconsistent`), so `/home` stops and says so. POS_CONFIGURED is the exception: A10 detects the same corruption itself and renders a terminal message, so routing there is safe and more useful than stopping. Resume is a read - no AuditLog row and no outbox event, because deriving a navigation target from existing state is not a state change and inventing a domain event for it would be speculative. No schema change was required: `Tenant.onboardingStep` plus Store existence already express everything the decision needs.
ADR-076 AMBURAX is a two-database system and the documents now say so. AMBURAX owns PostgreSQL; ERPNext requires and owns MariaDB. Until P1-7 this was true in fact and absent from every architecture document - `MariaDB` appeared in none of ARCHITECTURE.md, DATABASE_STRATEGY.md, DATA_STRATEGY.md, TENANT_ROUTING.md, SCALABILITY.md or MICROSERVICES.md. The boundary: PostgreSQL holds identity, tenancy, onboarding, device identity, audit and the outbox; MariaDB holds the stock ledger, accounting, tax, invoices and payments. Neither holds an authoritative copy of the other's domain, and cross-system links are mapping keys (`erpnextSiteId`, `erpnextWarehouseId`) rather than duplicated business data. There is no distributed transaction between them and none will be attempted; consistency is eventual through the existing durable outbox, and the UI must distinguish SERVER_ACCEPTED from ERP_VERIFIED rather than implying the ledger has the record when it does not. See ERPNEXT_ARCHITECTURE.md.
ADR-077 ERPNext tenancy is TIERED, with the Frappe site as the unit of tenancy at every tier. Tier 1 (default, small merchants): many sites on a shared bench, one MariaDB database per site. Tier 2 (high volume/multi-store): dedicated bench and MariaDB instance. Tier 3 (enterprise/regulated): dedicated infrastructure, own host/VPC/region. The tiers differ only in how much infrastructure a site shares - never in the logical model - so promotion is a migration rather than a redesign. Rejected: always-dedicated infrastructure (optimises for the rarest customer, ~100k benches to operate); shared-infrastructure-only (no answer for residency, contractual isolation or noisy neighbours); a single shared site with a tenant column on every DocType (one MariaDB holding every tenant's ledger, isolation resting on filtering ERPNext's own queries - one missing filter is a cross-tenant financial breach, per-tenant restore becomes impossible, and all tenants share one upgrade schedule); and replacing ERPNext with an Amburax-built ledger (contradicts ADR-001 and carries years of correctness and compliance risk). Mapping: Tenant 1:1 Frappe site, Tenant 1:1 ERPNext Company, Store 1:1 Warehouse; extra stores are extra Warehouses inside the same Company and site, never a second site. The Store->"Warehouse / Company setup" ambiguity in ERPNEXT_DOCTYPE_MAP.md is resolved by evidence: Store carries only `erpnextWarehouseId`, and DOMAIN_MODEL.md defines Tenant as the business/company shell.
ADR-078 Two P1-7 questions are deliberately left open rather than silently decided. (a) No `Tenant.erpnextCompanyId` column is added now - the mapping is decided but the column belongs in the first Phase-2 migration alongside the adapter that will populate it; adding a column nothing writes would repeat the orphaned-code mistake of P1-5. (b) Whether an online POS sale posts to ERPNext synchronously is a PRODUCT decision that the documents genuinely contradict: FLOWS.md and ARCHITECTURE.md read synchronous ("final sale, payment confirmation" listed under Synchronous), while OFFLINE_POS.md sections 16 and 27 define SERVER_ACCEPTED and ERP_VERIFIED as distinct states with the final state not accepted until authoritative verification. Ownership is settled either way - ERPNext owns the invoice - but whether the cashier waits is not derivable from the repository, and it must be answered before Phase 3. It does not block Phase 2. Also unresolved and recorded rather than assumed: the ERPNext hosting shape (managed vs self-hosted bench vs containers), and coordinated per-tenant backup/restore across two databases, for which no backup exists today at all.
